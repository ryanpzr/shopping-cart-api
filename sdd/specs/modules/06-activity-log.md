# Module: Activity Log

Audit trail of user actions (login, product changes, checkout, order cancellation), readable by admins.

## Dependencies
- `01-auth` — JWT middleware
- `02-user` — BR-ADMIN-006 endpoint is surfaced via the user module routes
- All other modules emit events into the outbox

---

## Architecture Decision

### Context

Every audited user action generates one extra record. At a scale of millions of actions, writing the audit log
synchronously into the main relational database, or publishing it synchronously to a broker inside the request,
puts a non-critical concern on the critical path of the request:

- **Synchronous insert into an audit table:** the audit table grows without bound in the transactional database,
  and audit queries compete with business traffic.
- **Synchronous publish to a broker inside the request ("dual write"):** the business data lives in PostgreSQL
  and the event lives in Kafka, and no transaction covers both.
  - *Commit, then publish:* if the publish fails, the order already exists but the event is lost (or the endpoint
    returns an error for something that did happen).
  - *Publish, then commit:* if the commit fails, the audit records an action that never happened.
  - Either way, the endpoint now depends on the broker's availability.

### Decision

Use the **Transactional Outbox** pattern with **Change Data Capture (CDC)**:

```
 ┌──────────── API (Go) ─────────────┐
 │ BEGIN                             │
 │   business write (order, stock…)  │
 │   INSERT INTO outbox_events (…)   │      same transaction:
 │ COMMIT                            │      both or neither
 └───────────────┬───────────────────┘
                 │ PostgreSQL WAL (logical replication)
                 ▼
     Debezium (Kafka Connect, Postgres connector + Outbox Event Router)
                 │
                 ▼
     Kafka topic: activity-log.events   (key = user_id)
                 │
                 ▼
     activity-consumer (Go, consumer group "activity-log-writer")
                 │  idempotent upsert by event_id
                 ▼
     MongoDB: activity_logs collection  ◄── GET /admin/users/:id/activity
```

1. The usecase inserts the event into `outbox_events` **in the same transaction** as the business change.
   The event exists if, and only if, the action was committed.
2. **Debezium** reads the outbox inserts from the PostgreSQL WAL. The application never talks to Kafka on the
   request path, so a Kafka outage does not affect the API: events wait in the WAL/outbox and flow once Kafka is back.
3. Delivery is **at-least-once**. The **consumer is idempotent**: a unique index on `event_id` in MongoDB turns
   redeliveries into no-ops.
4. MongoDB is the audit store: append-only, schema-flexible metadata, read by user and time range.

### Consequences

- (+) No dual write; audit is consistent with committed business state.
- (+) Request latency cost is one small append-only `INSERT` in an already-open transaction.
- (+) Broker or MongoDB outages never fail or roll back a user action.
- (+) Audit storage and reads are isolated from the transactional database.
- (−) **Eventual consistency**: an action may take a short time to appear in `GET /admin/users/:id/activity`.
- (−) More infrastructure to run: Kafka, Kafka Connect (Debezium), MongoDB.
- (−) `outbox_events` must be purged periodically (see below).

### Alternatives considered

| Option | Why not |
|---|---|
| Synchronous `INSERT` into `activity_logs` in PostgreSQL | Audit growth and reads load the transactional DB |
| Synchronous publish to Kafka in the request, return error on failure | Dual write: inconsistency on partial failure, and the API depends on broker availability |
| Fire-and-forget publish (goroutine) | Events lost on crash or broker outage — unacceptable for an audit trail |
| Outbox + polling relay in Go (instead of CDC) | Valid, but polling adds DB load and latency; CDC reads the WAL with no extra queries |

## Outbox (PostgreSQL)

```sql
CREATE TABLE outbox_events (
    id             UUID         PRIMARY KEY,           -- event_id, generated by the API
    aggregate_type VARCHAR(50)  NOT NULL,              -- e.g. 'user', 'product', 'order'
    aggregate_id   VARCHAR(50)  NOT NULL,              -- Kafka message key (user_id)
    event_type     VARCHAR(50)  NOT NULL,              -- see Event Catalog
    payload        JSONB        NOT NULL,              -- user_id, metadata, occurred_at
    created_at     TIMESTAMPTZ  NOT NULL DEFAULT NOW()
);

CREATE INDEX idx_outbox_events_created_at ON outbox_events(created_at);
```

- `aggregate_id` is the **user_id**, so all events of the same user land in the same partition, in order.
- PostgreSQL must run with `wal_level=logical` for Debezium.
- **Purge:** Debezium reads from the WAL, so rows are not needed after capture. A periodic job deletes rows
  older than 7 days (keeps a short window for debugging and replays).

### Emitting events

```go
// pkg/outbox/outbox.go
// Insert writes an event in the caller's transaction. It must be called
// inside the same *sql.Tx as the business change it describes.
func (w *Writer) Insert(ctx context.Context, e Event) error // Writer is bound to a database.DBTX (the tx)
```

```go
type Event struct {
    ID         uuid.UUID      // event_id
    UserID     int
    Type       string         // e.g. "cart_checkout"
    Metadata   map[string]any
    OccurredAt time.Time
}
```

Rules:
- Always pass the business transaction. If `Insert` fails, the whole transaction rolls back and the endpoint
  returns an error: an action without its audit event is not allowed.
- Read-only flows that must be audited (e.g. `login`) open a short transaction just for the outbox insert.

## Kafka

| Item | Value |
|---|---|
| Topic | `activity-log.events` |
| Key | `user_id` (ordering per user) |
| Dead-letter topic | `activity-log.events.dlq` |
| Connector | Debezium PostgreSQL connector, `pgoutput` plugin, table `public.outbox_events` |
| Transform | Debezium **Outbox Event Router** SMT (`aggregate_id` → key, `payload` → value, `id` → `id` header) |

---

## Consumer (`cmd/activity-consumer`)

- Separate Go binary, consumer group `activity-log-writer`.
- For each message: upsert into MongoDB by `event_id`, **then** commit the offset (at-least-once).
- A duplicate-key error on `event_id` means the event was already stored: treat it as success.
- Transient errors (MongoDB unavailable): retry with exponential backoff; do not commit the offset.
- Malformed messages (cannot be decoded): publish to `activity-log.events.dlq` and commit.

## Audit Store (MongoDB)

Collection `activity_logs`:

```json
{
  "_id": "ObjectId",
  "event_id": "0b6f…-uuid",
  "user_id": 42,
  "event_type": "cart_checkout",
  "metadata": { "order_id": 10, "total_price": 179.80 },
  "occurred_at": "2026-11-14T22:30:00Z",
  "ingested_at": "2026-11-14T22:30:01Z"
}
```

Indexes:
- `{ event_id: 1 }` **unique** — idempotency
- `{ user_id: 1, occurred_at: -1 }` — BR-ADMIN-006 listing
- `{ user_id: 1, event_type: 1, occurred_at: -1 }` — listing filtered by `event_type`

## Endpoint

The read endpoint is defined in `02-user` as BR-ADMIN-006 and registered under the `/admin/users/:id/activity` route.

| Rule | Endpoint | Method | Auth |
|---|---|---|---|
| BR-ADMIN-006 | `/admin/users/:id/activity` | GET | Admin |

- Reads from MongoDB (`activity_logs`), not PostgreSQL
- Returns paginated activity log for the given `user_id`
- Supports optional filter: `event_type`
- Ordered by `occurred_at DESC`
- Eventually consistent: very recent actions may not be listed yet

## Failure Modes

| Failure | Effect on the API | Effect on the audit |
|---|---|---|
| PostgreSQL down | Requests fail (as today) | No events — no actions happened |
| Outbox insert fails | Transaction rolls back, endpoint returns 500 | Consistent: no action, no event |
| Kafka or Kafka Connect down | **None** | Delayed: events stay in the WAL/outbox and flow on recovery |
| MongoDB down | **None** (writes); BR-ADMIN-006 returns 503 | Delayed: consumer retries, offsets not committed |
| Consumer crashes after writing, before committing offset | None | Redelivery, absorbed by the unique `event_id` index |

## Implementation Notes (Phase 4)

### Who owns an event
The `user_id` of an event is **whoever performed the action**. An admin who cancels someone else's order, or
deletes someone else's product, gets the event in the admin's own history; the other party is in the metadata
(`buyer_id`, `seller_id`). Only a successful `login` is audited, and registration emits nothing.

### Wire format
The outbox `payload` column, the Kafka message value and the MongoDB document are the same JSON:

```json
{ "event_id": "0b6f…", "user_id": 42, "event_type": "cart_checkout",
  "metadata": { "order_id": 10, "total_price": 179.8 }, "occurred_at": "2026-11-28T10:30:00Z" }
```

The Kafka key is `aggregate_id` (the `user_id`, as text). `aggregate_type` is `user` (login), `product`
(`product_*`), `cart` (`cart_checkout`) or `order` (`order_placed`, `order_cancelled`). The Debezium connector
(`deploy/debezium/outbox-connector.json`) uses string converters, so the message value is the payload text as is.

### Where each event is emitted
Every event is inserted through a `pkg/outbox.Writer` bound to the transaction of the change (`database.DBTX`):

| Event | Transaction |
|---|---|
| `login` | a single `INSERT` (atomic on its own); the login answers `500` and hands out no token if it fails |
| `product_created`, `product_updated` | product unit of work (`internal/product/shared`); update locks the product row |
| `product_deleted` | the `delete_product` unit of work (product row locked, orders checked, delete, event) |
| `cart_checkout`, `order_placed` | the checkout transaction, with the order, the stock and the closed cart |
| `order_cancelled` | `internal/order/cancellation`, shared by the buyer's cancel and the admin status change |

If the event cannot be written the whole transaction rolls back and the endpoint answers `500`.

### Metadata
`product_updated.changed_fields` lists the fields present in the request (JSON names, alphabetical).
`order_cancelled` carries `order_id` and `buyer_id`; `product_deleted` carries `product_id`, `title` and
`seller_id`; `cart_checkout` carries `order_id` and `total_price`.

### Consumer (`cmd/activity-consumer`)
- Reads `activity-log.events` in the group `activity-log-writer`; a new group starts from the beginning of the topic.
- Stores the entry **then** commits the offset. The store is an upsert with `$setOnInsert` on `event_id`, and a
  duplicate key counts as success, so a redelivery is harmless.
- A storage error is retried with exponential backoff (500 ms doubling up to 30 s) and the offset is not committed.
- A message that cannot become an entry (not JSON, missing or malformed `event_id`, no `user_id`, unknown
  `event_type`, no `occurred_at`) is published to `activity-log.events.dlq` with the headers `error` and
  `source-topic`, then committed, so it never blocks its partition. If the dead-letter publish fails, the message is
  retried like a storage error.
- A fetch or commit error makes the process exit and restart from the last committed offset.
- Configuration comes from environment variables (`KAFKA_BROKERS`, `KAFKA_TOPIC`, `KAFKA_DLQ_TOPIC`, `KAFKA_GROUP`,
  `MONGO_URI`, `MONGO_DB`); `MONGO_URI` is required.

### Read path
`GET /admin/users/:id/activity` (BR-ADMIN-006) reads MongoDB through `activitylog/shared.Repository`. The API
connects lazily and starts without MongoDB: if `MONGO_URI` is not set, or MongoDB is down, the endpoint answers
`503` with the fixed message `activity log is temporarily unavailable` (the cause is only logged) and every other
endpoint is unaffected.

### Outbox purge
The API deletes outbox rows older than 7 days every hour (`outbox.StartPurger`). The `DELETE` is idempotent, so
several API instances can run it at once. Debezium ignores the delete events.

### Running the pipeline
The pipeline is an optional compose profile, so `docker compose up` stays light (Postgres and the API):

```bash
docker compose --profile activity-log up --build
```

It adds Kafka (KRaft), Kafka Connect with Debezium, MongoDB, a one-shot job that creates the topics, a one-shot job
that registers the connector (a `PUT`, safe to repeat) and the consumer. Postgres always runs with
`wal_level=logical`.

Operational notes:
- **Replication slot:** the connector creates the slot `activity_log_outbox`. While the profile is stopped the slot
  keeps WAL on the Postgres volume; `docker compose down -v` removes it with the volumes.
- **Replay:** stop the consumer, reset the group (`kafka-consumer-groups.sh --reset-offsets --to-earliest`) and start
  it again: the unique `event_id` index absorbs everything already stored.
- **Local development only:** MongoDB and Kafka run without authentication, and the database password is the one in
  `docker-compose.yml`.
